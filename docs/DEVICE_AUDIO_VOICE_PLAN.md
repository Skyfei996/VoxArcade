# 两端界面、音效与语音操控方案

日期：2026-10-21。状态：老板已确认第 1–5 项，已实现并通过两端验证；第 6 项语音仅保留设计，未启用麦克风。详见 [PROTOTYPE_REVIEW.md](PROTOTYPE_REVIEW.md)。

## 1. 当前问题与已核对的事实

- 当前确实是同一份 index.html、app.js 和 styles.css，通过视口宽度切换布局，没有独立的 PC / 手机页面。CSS 历次覆盖叠加，PC 窄窗口会触发手机样式。
- 使用本机 Edge 在 615×973、DPR=1 下复现：无尽棋盘位图 800×1600；Canvas 元素框 515×386，但 object-fit:contain 后真正的棋盘图像只有 193×386。原来 1 个逻辑像素的格线最终约为 0.4825 个 CSS 像素；1440 宽时也只有约 0.52 像素。
- 因此本轮修复必须处理位图缩放与像素对齐，不能继续只改格线颜色。Canvas 元素框和内容图像尺寸不一致，还会影响当前步骤文字的坐标换算，一并修正。
- 615 宽的电脑窗口实测被 max-width:760px 识别为手机布局。复现截图：prototype/review/grid-before-615.png。本次没有读取用户会话、切换用户游戏或修改完成记录，测试使用独立浏览器上下文。
- 当前声音仅有通用 move、rotate、drop、clear、won、lost；左右及向下没有区分，受阻没有提示音，明确落地声音在指令开始时播放，自动接地和悬空固定缺少独立事件音。
- 本机 Edge 可检测到 SpeechRecognition 或 webkitSpeechRecognition 构造函数、getUserMedia 和安全上下文；仅说明 API 存在，尚未验证真实识别、语言或网络可用性，不能据此宣称语音已接通。

## 2. 代码边界与自动分流

把本轮“APP 端”按手机浏览器及添加到主屏幕后的网页体验设计，暂不制作 Android/iOS 原生安装包。

- 分为独立 PC 和手机 HTML、样式和视图交互；各自调整布局、面板行为、动画时长与触摸体验，不再靠同一份样式不断叠加断点。
- 共用游戏引擎、关卡、指令校验、事件和音效素材，保证两端碰撞、旋转、得分和解谜答案一致。复制两套游戏规则会带来规则漂移，不采用。
- 同一入口自动识别设备后加载对应页面。综合移动设备标识、触控能力及设备屏幕信息，适配平板；窗口宽度只影响所选页面内部的排版，不单凭宽度判断设备。PC 缩窄或缩放不能跳到手机页，手机横屏不能跳到 PC 页。
- 分流只在初始载入进行；旋转屏幕或调整窗口只重新计算棋盘大小，保留游戏与草稿。测试通过指定入口分别验证两套视图，不在运行期间重新载入页面。
- 实施前更新 AGENTS.md 的文件约定。拟在现有 prototype/ 内增加 desktop.html、mobile.html、desktop.css、mobile.css、desktop-view.mjs、mobile-view.mjs、entry.mjs；app.js 保留公共流程协调。仅在两个视图都验证正常后停止加载旧样式；不删除旧文件。

## 3. 棋盘与网格修复

1. 先根据棋盘列数/行数、当前视图可用宽高，计算等宽等高的格子及真实棋盘矩形；Canvas 元素尺寸与该矩形一致，不再让大元素框里包含 object-fit 产生的空白。
2. 根据实际显示尺寸及 devicePixelRatio 创建位图，格线在设备像素边界上对齐；每个边界只画一次，保证全部行列统一、清楚，不依赖浏览器缩放。
3. 格线线宽从屏幕显示尺寸出发设定，保持约 1 CSS 像素的可见宽度，再换算到设备像素；不将整张固定 800×1600 位图连同线宽一起缩小。
4. ResizeObserver、窗口大小变化、DPR/浏览器缩放变化后重算显示和位图尺寸。步骤气泡根据同一棋盘矩形定位，避免错位。
5. 棋盘必须保持实际列行比例。无尽为 10×20，仅扩大中间容器宽度不会让方块变大，还须释放垂直高度；不能横向拉伸成非正方格。

验收：正常缩放即可看清每行每列；检查 PC 615/1024/1366/1440/1920 宽，手机 320/375/390/430 宽，DPR 1/1.25/1.5/2/3，以及浏览器 80%/100%/125%/150% 缩放。像素截图抽查所有边界，不只检查 CSS 尺寸；保留问题前后截图。

## 4. PC 页面方案

- 主结构：左侧约 72–88px 单列栏，中间大棋盘，右侧约 280–320px 指令和流程。收紧顶部品牌、标题与说明的占高，把高度留给棋盘；具体尺寸按可用窗口约束计算。
- 无尽：后续五块沿左侧纵向排列，保留出场先后顺序。移除“填满一行即可消除。试试手动思考，或打开自动下落。”等占位说明。
- 闯关：左栏只保留一列关卡编号和完成状态；当前关名、必要目标放到棋盘上方的紧凑区域，避免长标题把栏撑宽。完整目标可展开查看。
- 棋盘居中，深色底框紧贴棋盘并留少量边距，减少现在大片无效的左右留白。用视口剩余高度决定棋盘尺寸，不固定为 445/470px。
- PC 窄窗口仍使用 PC 页面：缩窄间距或将流程详情折叠为侧面板，优先保留棋盘和操作；不得仅因窗口小于 760px 采用手机页面。
- 暂存功能在两端所有可见入口隐藏，包括当前方块旁交换按钮、暂存框和专用按钮；语音第一版也不提供暂存。不修复或删除底层 HOLD 逻辑，留待另行讨论。

## 5. 手机页面方案

- 顶部仅保留模式、关卡/得分、暂停/重开及设置的紧凑区域；大标题、装饰说明不占首屏高度。完整关卡列表放在选择面板，不常驻占高。
- 中部优先展示完整棋盘；库存/后续方块紧凑显示。以动态视口和安全区域计算剩余高度，浏览器地址栏展开/收起时不遮住棋盘底部。
- 底部操作区域在首屏内稳定可见，使用三列两行、大触控目标。流程列表默认显示数量及简短摘要，展开抽屉可查看、删除、排序；运行时自动收起，保留棋盘上的当前步骤和暂停入口。
- 目前普通操作需要在棋盘和控制台之间滚动；目标改为无需来回滚动就能选形、添加动作、落地。展开编辑流程是明确动作，不偷偷变更草稿或执行规则。
- 不通过压缩棋盘格子来容纳全部说明和完整流程列表。优先减少外框、重复信息和面板占高，保持完整棋盘及操作区可用。
- 在 390×844 手机模拟视口，无尽棋盘目标高度约 480–520px（目前约 344px 内容高度），最终以安全区域、按钮至少 44px 和不遮挡为准。横屏采用手机专属横排布局，不切换为 PC 视图。

按钮位置按截图中两按钮交换理解，不改变移动格数：

| 左列 | 中列 | 右列 |
| --- | --- | --- |
| 左移 | 右移 | 下移 |
| 顺转 90° | 逆转 90° | 落地并提交 |

PC 按同一顺序排布；按钮上的格数继续随格数选择器变化，不把下移写死为两格。

## 6. 音量翻倍及完整音效设计

背景音乐与游戏音效统一增加 2 倍输出增益，保留两个独立开关及消行行数对应的强弱变化。混音时控制最大峰值，避免多音叠加后破音；不要求用户把系统音量开到最大。“2 倍”以应用音频增益为可验证标准，不承诺不同扬声器上的主观响度严格翻倍。

| 事件 | 设计与触发时机 |
| --- | --- |
| 左移 / 右移成功 | 两种音高方向不同的短音，仅在动作实际执行时播放 |
| 手动下移 | 较低的短促音，与横移区分；一条指令播一次，不按每格叠加 |
| 顺转 / 逆转成功 | 上行 / 下行的轻快转动音，与移动声不同 |
| 横移碰墙或碰固定方块 | 短促钝响；对应整步无效，不播放成功移动声 |
| 旋转受阻 | 与横移受阻不同的双短音；一次失败播一次 |
| 快速落地 | 开始时快速下降音，实际落到目标时播放落地撞击声，避免还在顶部就听到落地声 |
| 下移或自动下降接地 | 实际接地时播放落地声；碰到已有方块同样适用，不只棋盘底部 |
| 自然结束时悬空固定 | 轻微锁定音，与落到底部的撞击声区分 |
| 自动下降中间格 | 默认不逐格鸣响，避免最高速度每秒十次声音淹没其他提示；接地仍有音效 |
| 消除 1/2/3/4 行 | 分层的消除音，行数越多越强，保持与过关旋律明显不同 |
| 过关 / 失败 | 独立的完整收尾音，不复用四行消除的同一旋律 |
| 暂停 / 继续、无效输入 | 简短状态提示，不覆盖关键游戏反馈 |
| 选形与草稿按钮 | 仅轻微操作确认声，不提前播放动作执行声；不会把编排误听成执行 |

音效通过统一游戏事件触发，不在 render 中播放。处理优先级及短时合并：结算 > 消行 > 落地 > 移动/UI；同一次落地提交不叠加两次撞击，旋转失败不混入成功旋转音。语音录入时临时静音音乐和游戏音效，识别结束后按原开关恢复，避免放大后的音效被麦克风收进去。

验收：与旧版同一合成声音测量 2 倍增益；逐项触发成功、受阻、接地、悬空固定和结果事件，验证音色/节奏差异及实际音频输出。混音不削波，开关仍独立有效；测试环境与未做的物理试听如实记录。

## 7. 语音操控方案（本轮只设计）

### 两端的实际要求

| 项目 | PC 网页 | 手机网页 |
| --- | --- | --- |
| 麦克风 | 系统及浏览器权限、正确输入设备 | 系统及浏览器权限，受页面前后台状态影响 |
| 页面来源 | 本机 localhost 是可用于开发的安全上下文；联网正式访问用 HTTPS | 访问电脑的局域网 IP 是远程来源，普通 HTTP 不满足标准麦克风采集的安全上下文要求；需要可信 HTTPS |
| 识别能力 | 必须检测当前浏览器接口及真实服务可达性；本机 Edge 仅已验证接口存在 | Android 浏览器和 iOS Safari 分别实测；不能因都是网页就认定服务、语言和连续监听行为一致 |
| 生命周期 | 切换后台、权限拒绝、识别终止须明确反馈 | 另测锁屏、切应用、横竖屏、耳机切换及系统打断；不承诺后台持续监听 |
| 内嵌页面 | 麦克风权限还受宿主容器策略影响 | 内嵌浏览器/WebView 也需宿主允许，不能当作独立 Safari/Chrome 等同支持 |

依据：标准麦克风采集要求安全上下文和用户授权，localhost 可作为开发例外，电脑的局域网 HTTP 地址不能等同为手机的 localhost。[MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)。

浏览器原生 SpeechRecognition 并非全平台一致可用，部分实现会将音频发往远端服务；不应承诺离线或仅本机处理。[MDN SpeechRecognition](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition)。Safari 已有基于 Siri 的实现，厂商说明涉及系统 Siri 条件，实际设备仍需验证。[WebKit 说明](https://webkit.org/blog/11648/new-webkit-features-in-safari-14-1/)。

### 接入路线与推荐

| 路线 | 收益 | 约束 | 建议 |
| --- | --- | --- | --- |
| 浏览器原生识别 | 无需应用自建转写服务或保存服务密钥，适合验证本项目短指令 | 识别服务由浏览器/系统决定，网络、语言及手机生命周期差异仍存在 | 第一版推荐先做目标设备真实可行性验证，再接入 |
| 统一云端识别（Azure Speech 可作为候选） | PC/手机采用同一服务，便于统一语言和词汇 | 需要服务账号、后端鉴权、网络与费用评估，也仍需 HTTPS 和麦克风权限 | 若原生路线不能覆盖实际设备，再单独确认接入；不同时实现两套服务 |

Azure JavaScript SDK 支持浏览器场景，官方提供浏览器示例；鉴权采用服务端换取短期凭证，不将长期密钥放进网页。[SDK 官方仓库](https://github.com/microsoft/cognitive-services-speech-sdk-js)、[官方鉴权示例](https://github.com/Azure-Samples/AzureSpeechReactSample)。后者已归档，只参考鉴权模式，不复制它的 token 日志、长期存储方式或依赖版本。

本轮不创建云账号、不安装 SDK、不修改 .env/密钥、不配置证书或系统信任，也不公开部署 HTTPS 环境。手机 HTTPS 的提供方式属于语音接入前置事项，实施时单独确认；不能为绕过权限而让用户关闭浏览器安全设置。

### 第一版操作与指令

1. 提供中文 / English 选择；第一版不承诺一句内混说或自动语言判断。默认未开启；先提示音频可能由浏览器/服务商处理，用户点击后才请求权限。
2. 两端均先采用“按住说话，松开发送”，支持一条或一串短指令，减少手机端连续监听终止及音乐回声的问题。录音中显示识别文字，临时结果不改草稿。
3. 最终识别结果用确定性语法转成已有指令：选形、左/右/下移格数、顺/逆转 90°、落地提交。普通指令追加草稿；明确说“落地提交”才像同名按钮一样运行本轮全部步骤。也支持“运行流程”启动已有草稿，流程暂停/继续仍使用现有按钮。
4. 例如“选 T，右移两格，顺时针旋转，落地提交”，解析成 SELECT_PIECE、MOVE_RIGHT(2)、ROTATE_CW、HARD_DROP。整句先解析并校验，再一次性追加；若有不明词或越界格数，整句不生效并显示可修改的转写，不执行半句后误提交。
5. 避免“下移两格”和“落地提交”混淆；只有明确提交词才执行 HARD_DROP。数字缺省及范围沿用按钮规则，不默默截断。固定顺序关卡不能用语音改选，暂存不进入首版语法。
6. 已启动的流程（包括暂停）以及结算动画期间不接收编排语音，不允许通过语音改写正在执行的计划；本轮结束后重新开放。运行中的暂停/继续使用可见按钮。语音会话绑定当前局、方块和草稿版本；同一识别回调按会话与结果序号去重，切局后的迟到结果丢弃。玩家再次主动说相同命令仍是有效新输入。
7. 松开发送并收到识别终止后释放本轮麦克风；重开、切局、后台、关闭语音时停止采集。识别失败、断网、权限拒绝或意外终止均显示原因并暂停语音，不悄悄换识别服务或无限重启。用户可明确关闭语音，再用按钮继续。
8. 不保存原始录音和真实转写，不把任何密钥或凭证写进日志。语音识别和设备页面分开选择：PC/手机视图不同，但最终都进入同一个命令校验器和游戏引擎。

### 验收门槛

- 首先在实际 Windows 浏览器、Android 手机和 iPhone Safari 中确认接口、权限、HTTPS、中文/英文服务及网络可用性。无法实际验证的设备标记未验收，模拟器不冒充实机。
- 合成输入检查：正常、含糊、非法格数、混合多步骤、重复回调、迟到回调、固定队列拒绝改选、HARD_DROP 只触发一次，均与按钮行为一致。
- 真机语音检查：每个目标平台分别用中文和英文各完成至少一局；记录错误类型、最终结果延迟及成功率，拒绝用按钮完成后声称语音通关。
- 手机打断、拒绝权限、网络中断、关闭音频、关闭语音、重新开启都必须恢复到可理解的状态。背景音乐不应被识别成命令。

## 8. 实施顺序与审批边界

1. 确认本方案后，先更新 AGENTS.md 的双端页面、暂存隐藏及音效事件约定，再实施第 1–5 项界面和音频改动。
2. 先修网格及真实棋盘矩形，再分 PC/手机视图，最后接入音效事件及按钮新顺序，避免重复修同一坐标问题。
3. 两端分别回归八关、无尽手动/自动下落、动画、暂停、旋转演示及库存；对比同一事件与流程的结果，确认只改显示和声音，不改游戏规则。
4. 语音本轮只交付设计。接入前先确定目标设备和可信 HTTPS 测试方式，进行真实可行性验证；涉及系统、密钥和发布的步骤另行批准。

技术依据另见 [Canvas 优化](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)、[devicePixelRatio 与页面缩放](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio)。
